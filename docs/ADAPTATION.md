# 游戏更新后的适配

目录名称／编号更新和原生引擎适配分别维护。目录由 `cargo xtask update-catalog` 在发版时更新；不要把目录版本当成 EXE 兼容性证明。

## 相关代码

| 位置 | 作用 |
| --- | --- |
| `data/builds.json` | 已适配构建的版本与磁盘 SHA256；用 `cargo xtask build-id <EXE>` 生成条目 |
| `crates/skinlab-core/src/protocol.rs` | host 会话 JSON 协议的 Rust 端定义 |
| `native/src/profile_rules_generated.cpp` | 已恢复并提交的机器码特征与解析配方；构建直接使用，无需原 DLL |
| `native/src/profile_scan.cpp` | 匹配特征、解析 RIP 相对位移／字段偏移／编码参数 |
| `native/include/skinlab/league_fields.h` | CharacterDataStack 内部成员偏移 |
| `native/loader/game_session.h` | 解析运行时对象、建立会话、把命令交给帧回调 |
| `native/src/core.cpp` | 编号编码、快照、应用、刷新及恢复 |
| `native/src/dx11_bridge.cpp` | 在 DX11 Present 所在线程处理更新命令 |

host 以 `--session` 启动时，接入失败也必须返回 `event: "session"` 的单行 JSON（尚未建成会话时用 `state: "invalid"` 并携带 `error`），不能返回普通观察报告。控制器据此分类错误；英雄尚未载入时等待重试，版本或关键特征检查失败时停止接入。`cargo xtask verify` 同时检查启动失败协议与正常 fixture 会话。

适配时可向新的 host 会话发送 `inspect`：命令在已有帧线程执行，返回 `stack_probe`，包括 stack 的 176 字节前缀、长度不超过 64 KiB 的候选层区间的头尾各最多 256 字节，以及 push、update、调用点上下文、层析构和 gear 处理函数各最多 4096 字节代码。代码和对象跨度均回读；回读变化、区间无效或目标改变会分别标记，失败采样不会复用旧序号。原始字节及回读一致仅用于分析，不证明结构布局或引擎调用语义。观察模式的 `--probe-code` 只在采集线程读取这些代码，不建立帧会话、不调用引擎。共享内存协议为 v7，host、DLL 和 fixture 必须同步重建。UI 不提供采集命令；实际游戏采集仍须安排训练模式。

元素使拉克丝：16.21 运行时代码确认层步长 `0xA0`、层内 skin `+0x20`、gear `+0x84`（基础层从 stack `+0x18` 起），push 有 18 个参数且内部执行 update，末参数为字符串。`owned_layer.h` 按引擎 push 建层、按引擎析构释放；仅接受初始额外层为空且基础 gear 为 `0xFF` 的状态，已有层归属或内容变化时拒绝释放。运行时 push、update 和析构完整函数指纹均匹配才启用特殊路径，普通皮肤仍共用原流程。

会话命令 `form LuxAir` 等仅选择 WAD 已确认的九个模型别名，`form Lux` 清除自建层，`restore`／`stop` 同时恢复皮肤；不把资源数组顺序当作 gear 编号。host 通过 `available_forms` 宣告能力，界面仅在选中 Lux skin 7 且能力可用时提供形态下拉框。训练模式已抽查光、风、火及 Q/W/E/R、形态互切和恢复；恢复后额外层为空、基础数据还原，容器可保留引擎分配的容量。自建 fixture 检查 18 参数打包、重复选择、层替换／释放、外部改写和目标失效。

## Agent 的工作顺序

1. 确认新 EXE 版本和完整 SHA256，保留旧配置以便比较。先在新二进制中检查相关函数和数据布局；用户准备训练模式后再获取必要的运行时证据。
2. 核对六项关键配方：本地玩家全局引用、CharacterDataStack 对象偏移、编码皮肤字段、stack 更新函数、MaterialRegistry getter、交换链字段。关键规则必须得到唯一且回读一致的结果；不相关的英雄列表或翻译函数模糊匹配不必阻塞当前玩家路径。
3. 失效规则应从原函数上下文、调用者和访问字段的指令重新定位。读出 RIP 相对位移、字段立即数及旋转／异或参数，更新特征和解析逻辑。无法确定的字段不要用旧值猜测。提交的规则文件虽叫 generated，后续可以维护其内容；重新提取脚本不是构建依赖。
4. 分清三类数字：RVA 加模块基址得到全局变量／函数；对象偏移加对象地址得到成员；指令内的字节位置用于解析立即数，两者不能混用。`league_fields.h` 的模型指针和 stack 皮肤成员属于结构成员，需要独立确认。
5. 核对本地玩家指针、模型名及两个皮肤字段的一致性，核对编解码互逆、stack 更新调用约定和交换链所有权。刷新应在实际帧线程上执行；不要让 UI 或采集线程直接调用引擎更新函数。
6. 完成代码适配后再把 `cargo xtask build-id` 的输出加入 `data/builds.json`（旧构建条目保留到确认不再需要）。重新构建，运行 `cargo test --workspace` 与 `cargo xtask verify`；与用户安排训练模式，抽样确认应用、恢复、技能外观和退出行为。
7. 更新当前支持范围和 TODO，提交相关代码及目录数据。不要新增逐英雄测试台账，也不要把本地样本／分析报告上传仓库。未完成真实验证时如实说明。

旧版地址只是某个构建的结果，ASLR 下不能直接拿它当绝对地址。当前方案通过运行时代码特征计算所需参数，仍需人工／Agent 对版本变化作判断，不具备全自动跨版本兼容能力。不要通过关闭或绕过反作弊来完成适配。

普通皮肤的共用流程是：当前玩家对象 → 读取原状态 → 编码并设置目标编号／stack 字段 → 帧线程调用刷新 → 保存可恢复状态。特殊模型、装备／形态、技能资源或多层 stack 可能需要额外处理，不能只更新编号就宣称支持。
